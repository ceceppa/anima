The two callback fields are optional `Callable`s invoked by `AnimaPlayback`, not signals — see §Target-bound authoring contract. | `AnimaValue` | `kind: Kind` (source: `CONSTANT`/`TARGET`/`NODE`/`ROOT`/`CONTEXT`/`GROUP_INDEX`/`GROUP_COUNT`/`GROUP_NORMALISED_INDEX`/`GRID_ROW`/`GRID_COLUMN`; arithmetic: `ADD`/`SUBTRACT`/`MULTIPLY`/`DIVIDE`/`NEGATIVE`/`ABSOLUTE`/`MINIMUM`/`MAXIMUM`/`CLAMP`/`MAP`/`COMPONENT`; escape: `CUSTOM`), `constant_value: Variant`, `property_path: NodePath`, `node_path: NodePath`, `context_key: String`, `operands: Array` (each entry a literal or a nested `AnimaValue`; index 0 is always the value the chain method was called on — `CLAMP` is `[value, min, max]`, `MAP` is `[value, in_min, in_max, out_min, out_max]`), `component_index: int`, `custom_callable: Callable` | One polymorphic Resource, the same "one class, a `Kind` discriminator" shape `AnimaEase` already uses — see §Dynamic values. |
| `AnimaValueContext` | `target: Node`, `root: Node`, `context_data: Dictionary`, `group_index: int` / `group_count: int` (`-1` outside a group item), `group_normalised_index: float` (`-1.0` outside a group item), `grid_row: int` / `grid_column: int` (`-1` outside an `AnimaGridMotion` item) | Transient `RefCounted`, built fresh per resolution — never serialized, never authored. |

`playback_mode` is `SEQUENTIAL`, `PARALLEL`, or `STAGGERED`. Staggered playback uses exactly one distribution mode: `FIXED_INTERVAL` or `TOTAL_DURATION`. Its interval and total-duration fields own the corresponding delay; `sequential_gap` owns the post-completion delay.

`order.kind` is forward, reverse, centred, edge, random, grid, distance, explicit, or custom. `order.origin` is `FIRST`, `LAST`, `CENTER`, `INDEX`, or `POINT`; index and point values are required only for their matching origin. Grid columns own non-inferred grid resolution. A seed makes random order deterministic and is retained in the execution record.

`AnimaGridMotion.grid_dimensions` owns the authored grid width and height. Both values must be positive; resolved children fill cells in row-major order, and a partially filled final row is valid. When the target is a `GridContainer`, its configured column count is used only when the authored dimensions are absent. `start_point` owns the zero-based grid coordinate from which distance is calculated, and must be inside `grid_dimensions`. `distance_formula` defaults to `ROW` and `start_point` defaults to `(0, 0)` — together the "defaults to `FROM_TOP`" propagation the phase brief describes: row 0 starts first, each following row one wave later. `spiral_direction` defaults to clockwise. The grid showcase's 5×5 layout is a demo scenario, not a runtime limit.

## Easing curve library

`AnimaEase.Kind` gains 33 new named values alongside its existing ones (`LINEAR` already covers the identical `t -> t` case, so it is not duplicated): `EASE`, `EASE_IN`, `EASE_OUT`, `EASE_IN_OUT`, and the `EASE_IN_*`/`EASE_OUT_*`/`EASE_IN_OUT_*` triad for `SINE`, `QUAD`, `CUBIC`, `QUART`, `QUINT`, `EXPO`, `CIRC`, `BACK`, `ELASTIC`, and `BOUNCE` — the full curve vocabulary the phase brief restores, matching each name exactly so existing author knowledge (and any code) carries over directly. Each evaluates its curve's standard closed-form definition (the well-known Penner/CSS easing equations) for `AnimaEase.evaluate(t)`; the existing family-plus-parameter `Kind` values (`POLYNOMIAL`, `SINE`, `EXPONENTIAL`, `CIRCULAR`, `BACK`, `BOUNCE`, `ELASTIC`, `CUBIC_BEZIER`, `CURVE`, `CALLABLE`, `DECAY`, `CUSTOM_SAMPLED`, `SPRING`) are unchanged and keep their current single-shape behaviour for existing callers. `EASE`/`EASE_IN`/`EASE_OUT`/`EASE_IN_OUT` use the quadratic curve shape (the same shape as their `_QUAD` counterpart) — a common default for a bare "ease" across engines and CSS.

⚠️ Note: the bare `EASE`/`EASE_IN`/`EASE_OUT`/`EASE_IN_OUT` → quadratic mapping is a reasonable default, not verified against the original Anima v1 source (unavailable). Low-risk to retune later — it changes a curve shape, not a public signature.

The Property Motion Composer's ease picker already builds its list from `AnimaEase.Kind.keys()` (`anima_property_motion_composer.gd`), so the new values appear there automatically — no Composer change is needed for this addition.

`AnimaEase.from(value: Variant) -> AnimaEase` is a static factory scoped to phase-14's own convenience `with_ease()` methods below (`AnimaKeyframeMotion.with_ease()`, `AnimaGridMotionFactory.with_ease()`) — not a change to `AnimaPropertyMotion.ease`/`.with_ease()`, which are untouched. Returns `value` unchanged when it's already an `AnimaEase`; wraps a bare `AnimaEase.Kind` value in a fresh `AnimaEase` (`kind = value`, every other field at its own default) otherwise, so a caller who only needs a named curve — the common case, e.g. `AnimaEase.Kind.EASE_IN_OUT` — never has to construct and configure a whole resource by hand for it (v1 accepted a bare curve identifier the same way). Reports an error and returns a default `AnimaEase.new()` (`LINEAR`) for any other input type, rather than silently misbehaving.

## Motion pivot control

`AnimaPivot` is a standalone, non-`Resource` helper class (`motion/resources/`, the same kind of helper `AnimaEase`/`Motion` already are) holding `enum Kind { NONE, TOP_LEFT, TOP_CENTER, TOP_RIGHT, CENTER_LEFT, CENTER, CENTER_RIGHT, BOTTOM_LEFT, BOTTOM_CENTER, BOTTOM_RIGHT }`. Replaced the earlier `AnimaPropertyMotion.Pivot` nested enum in phase-15 — same values, same ordinals, moved out from under an unrelated motion class so every consuming field (`AnimaPropertyMotion.pivot`, `AnimaKeyframeMotion.default_pivot`, `AnimaKeyframeStop.pivot`) reads `AnimaPivot.Kind` instead of naming a class that isn't conceptually theirs. `AnimaPropertyMotion` gains a `pivot: AnimaPivot.Kind` field, default `NONE`. It only takes effect when the motion's canonical property is `scale`/`scale:x`/`scale:y` or `rotation`, resolved once when the motion's runtime instance begins advancing (the same "resolved once at start" timing `from_value` already uses), against the target's size at that moment. Two target categories resolve it, confirmed against Anima v1's own `set_2D_pivot()`:
- **`Control`** — resolves the 9 anchor positions against `size` (`TOP_LEFT` = `Vector2.ZERO`, `CENTER` = `size / 2.0`, `BOTTOM_RIGHT` = `size`, and so on) directly into Godot's native `Control.pivot_offset`, which Godot's own rendering already uses as the scale/rotation origin — no per-frame compensation needed.
- **A 2D node exposing both `offset: Vector2` and `texture: Texture2D`** (`Sprite2D`, `AnimatedSprite2D`, and similar — detected by property presence, the same way as the Inspector entry point) — has no native pivot, so `pivot` shifts the node's own `offset` and compensates `global_position` once at motion start so the artwork doesn't visibly jump, the same technique v1 used; size is `texture.get_size() * node.scale`.

`pivot` is silently ignored (not a validation error) on any other property or target class — including a plain `Node2D` with no `texture`/`offset`, which has no inherent size to resolve a named anchor against — the same way `is_relative` is inert where it doesn't apply.

⚠️ Note: v1's pasted `set_2D_pivot()` also cached the size it last applied pivot at (in node meta, with a separate editor-hint key) to skip reapplying when unchanged — a guard against being called repeatedly from an unspecified call site. Anima 2 doesn't need it: pivot resolves exactly once, when the runtime instance begins advancing, never on every frame or every call.

⚠ Verify: the pasted v1 code's `BOTTOM_CENTER` (`size.y / 2`) and `BOTTOM_RIGHT` (`size.y / 2`) `Control` cases look inconsistent with `BOTTOM_LEFT`'s own `size.y` (full height) and with what "bottom" implies — this spec uses `size.y` (full) for all three `BOTTOM_*` positions instead of reproducing what looks like a copy-paste bug in the reference. Flag if that halving was actually intentional.

**Shared with keyframe motions (phase-14).** The anchor table, the `Control`/offset-pivot branching, and `_supports_offset_pivot()` move from `AnimaPropertyMotionInstance` up to the shared `AnimaMotionInstance` base as `_apply_pivot_to(target: Node, pivot: AnimaPivot.Kind) -> void` — the same base class §Dynamic values already added `_resolve_dynamic()` to. It takes just `target` and an already-resolved `pivot`, not a whole motion: `AnimaPropertyMotionInstance._apply_pivot()` becomes a thin wrapper that keeps its own `scale`/`rotation` `target_property` gate before calling the shared method; `AnimaKeyframeMotionInstance` calls the same shared method with its own gate (§Keyframe motions, "Pivot"). Neither caller's own resolution timing or gating logic changes — only the anchor math and target-branching move to one place instead of being duplicated.

## Motion Composer entry point

`AnimaMotionInspectorPlugin._can_handle(object)` (`addons/anima/anima_plugin.gd`) currently returns true only for `object is AnimaMotion` — reachable only by first expanding an `AnimaMotion` *resource field* in the Inspector, with no path in from the node itself. It now also returns true for a `Node` whose script exposes at least one exported property typed as `AnimaMotion` (or a subtype), detected via `get_property_list()`'s `PROPERTY_HINT_RESOURCE_TYPE` hint. For such a node, `_parse_begin` adds an "Anima" Inspector section listing each matching motion field by name with an Open Motion Composer action; a field currently holding `null` shows a short message instead of a disabled dead end ("Assign an Anima motion to open it here"). A node with zero motion fields is not handled, unchanged from today.

`AnimaMotionComposer`'s own top-level empty state, and `AnimaGroupComposer`'s "no group selected" state, each name the concrete next action reachable from exactly that state (open a motion from the Inspector or select a node with one; pick a different motion from the graph or add a group to the current selection) instead of a message with no path forward — the exact copy is implementation detail, the contract is that every such state names a reachable next action (see `project-rules.md` §Editor Boundaries).

## Group animation semantics

The former v1 animation types are expressed as resource configuration, never as a compatibility enum or API:

| v1 behaviour | Anima 2 semantics |
|---|---|
| FROM_TOP / FROM_BOTTOM | `FORWARD` / `REVERSE` resolved order with a first-origin stagger |
| FROM_CENTER | centre origin; distance from the middle determines rank |
| TOGETHER | `PARALLEL`; all stagger settings are ignored |
| ODDS_ONLY / EVEN_ONLY | index-parity target filter before ordering and scheduling |
| RANDOM | seeded random order, retained for replay and reverse |
| FROM_INDEX | index origin; rank is absolute distance from the chosen resolved-list index |

Even-centre targets share rank zero. An index origin ranks by absolute distance, so equal-distance targets begin as one wave; grids use the same rule. “Top” and “bottom” mean resolved collection order unless an explicit spatial order is selected.

`order.origin = FIRST` is the default when no origin is specified, matching top-to-bottom list traversal.

## Target-bound authoring contract

`Anima.on()` is a convenience factory, not a new motion representation. Each semantic method creates the same canonical property motion that direct `Motion.to()` authoring would create; the factory does not retain playback state or require a separate runtime path. `Anima.on(target) -> AnimaOnMotionFactory` and `Anima.item() -> AnimaItemMotionFactory` are lightweight `RefCounted` builders under `motion/runtime/` — the same kind of runtime-facing helper as the existing `AnimaNodeProxy`, not `AnimaMotion` subtypes. `Anima.on(null)` reports an error and returns `null` immediately rather than deferring the null check to the first property call. The initial semantic set is position, relative movement, scale, rotation, opacity, colour, size, and a generic property escape hatch.

`Anima.item()` produces the equivalent item-bound property motion for a group and cannot be saved as a fixed-node reference. Its `AnimaTargetReference` uses the existing `PLAYBACK_CONTEXT` resolution mode, resolved per item by the group scheduler when it creates that item's runtime instance — the same mode a directly-supplied playback target already uses, so no separate group-item resolution mode is needed. A convenience-created motion carries optional editor-only origin metadata for display, but its property path, values, timing, and target reference remain canonical resource data.

`AnimaPropertyMotion` gains one new field this phase: `is_relative` (`bool`, default `false`). When `true`, `to_value` is added to the resolved start value instead of replacing it. `move_by()`, `scale_by()`, and `rotate_by()` set it internally; the generic `.relative()` modifier exposes the same behaviour for `.property()` and other semantic methods.

An omitted start value means `CURRENT_AT_MOTION_START`; an explicit `.from()` means `EXPLICIT`. The resolved start value is retained in the execution record so reversal returns to what was actually observed at playback start. Convenience motions use the standard relationship composition, validation, and native-compilation paths with no special cases.

`AnimaMotion` gains two new chain methods, usable on any motion (canonical or convenience-created), building the same `_AnimaSequence`/`_AnimaParallel` resources direct construction would: `.then(other)` appends `other` as a new sequential step (flattening a repeated `.then()` chain into one flat `_AnimaSequence`, not nesting); `.with(other)` folds `other` into the same `_AnimaParallel` group as whatever was most recently chained — the parallel group open since the last `.then()`, or the whole chain when no `.then()` preceded it. Chaining a second semantic method directly (e.g. `.position().opacity()`) stays unsupported: the first call already returned a motion, not the factory, so combining two properties always goes through `.then()`/`.with()` explicitly.

**Chaining a motion *factory* directly (phase-15).** `.then(other)`/`.with(other)` accept `other: Variant`, not just `AnimaMotion` — `other` may also be any object exposing a `motion: AnimaMotion` property (the established convention every convenience factory already follows: `AnimaGridMotionFactory.motion`, `AnimaGroupMotionFactory.motion` (§Group convenience shorthand), and any future factory built the same way). Resolution: if `other is AnimaMotion`, used directly; else if `"motion" in other` and that property holds an `AnimaMotion`, that resource is used; else `.then()`/`.with()` report an error naming the unsupported type and return `self` unchanged (no crash, no silent no-op — the same posture every other chain-method error case in this spec uses). This is what lets `Anima.on(a).move_by(...).with(Anima.grid(b).radial())` and `Anima.grid(a).radial().then(Anima.grid(b).diagonal())` both compile and play directly, with no `.motion`/`.play()` unwrapping needed at the call site. `AnimaGridMotionFactory.then()`/`.with()` (§Grid convenience shorthand) delegate to this same resolution, so a factory-to-factory chain works identically whichever side the call starts on.

**`.play()` and per-leaf convenience targets (phase-15).** `Anima.on(target)` captures `target` on every motion its semantic methods build — a transient, non-exported `convenience_target: Node` field on `AnimaMotion` itself (not only `AnimaPropertyMotion`), read by `.play()` below and never serialized, per this section's own "transient direct target, immediate playback only" rule. `AnimaMotion.play() -> AnimaPlayback` starts the motion immediately via `Anima.play(self, target)`, the fluent counterpart to a separate `Anima.play(motion, target)` call — `target` is `self.convenience_target` when set, or `null` otherwise (`Anima.play()` already accepts `target = null` for a motion supplying its own targets, per §Playback interface). Reports an error and returns `null` only for a leaf `AnimaPropertyMotion` with no `convenience_target` — a hand-built canonical motion still needs `Anima.play(motion, target)` directly.

`.then(other)`/`.with(other)` propagate `convenience_target` onto the `_AnimaSequence`/`_AnimaParallel` they build only when every combined motion shares the exact same one (the common case: chaining multiple `Anima.on(sameNode)`-built motions). Combining motions built against *different* targets — e.g. `Anima.on(a)....with(Anima.on(b)....with(Anima.on(c)...))` — leaves the composite's own `convenience_target` unset, and that's sufficient: target resolution happens per leaf, not once at the composite root. Every leaf instance's `advance()` (and `restore_initial()`/`force_complete()`/pivot application) resolves against its *own* motion's `convenience_target` when set, falling back to whatever target the enclosing `AnimaPlayback` supplies only when a leaf has none of its own. A canonical, hand-built leaf (via `Motion.to()` etc., no captured target) is unaffected — it always uses the playback-supplied target, exactly as before this phase. This is what makes `.play()` reachable on a `.then()`/`.with()` composite of independently-targeted convenience motions, with no per-leaf `Anima.play()` call needed: `Anima.on(a).move_by(...).with(Anima.on(b).move_by(...)).with(Anima.on(c).color(...)).play()`. If a composite genuinely contains a leaf with neither its own captured target nor a usable root target, the failure surfaces at `advance()` time exactly as it would for any incorrectly-targeted canonical motion today — this phase adds no new validation path for that case.

`AnimaMotion` gains four more chain methods alongside `.then()`/`.with()`: `.on_started(callback: Callable)` and `.on_completed(callback: Callable)` store `on_started_callback`/`on_completed_callback` and return self; `AnimaPlayback` calls `on_started_callback` once at `_init` and `on_completed_callback` once immediately before `finished.emit(true)` — never on cancellation, the same `success` distinction `finished` already draws. These are declarative, baked into the motion resource, and sit alongside the existing `finished` signal rather than replacing it. `.repeat(count: int = -1, alternate: bool = false)` wraps the motion it's called on in a new `_AnimaRepeat` and returns that — the same wrapping `Motion.repeat(child, count)` already builds, now reachable as a chain call on any motion, including one built through `Anima.on()`; this replaces the earlier "not exposed on the factory" note (superseded in phase-10). `.with_speed(value: float)` sets the existing `speed` field via the established `with_` naming.

**Child callbacks inside a composite (phase-15).** `AnimaPlayback` only ever calls back on its *root* motion — a callback set on a motion *before* it was folded into a `.then()`/`.with()` composite previously never fired once wrapped, since nothing else invoked it. `AnimaSequenceInstance`/`AnimaParallelInstance` now fire each child's own `on_started_callback`/`on_completed_callback` directly, independent of whatever the root's own callbacks are: a sequence child fires `on_started` the instant its own scheduled start arrives (and `on_completed` the instant its own `advance()` first reports finished); a parallel child fires `on_started` the instant it starts — immediately at construction when its own `delay <= 0.0` (the default; every enabled child starts together, unchanged from before), or once its own `delay` has elapsed otherwise (see "Per-child delay inside `.with()`" below) — and `on_completed` the instant its own `advance()` first reports finished. Each fires at most once per child, mirroring the existing root-level `finished`/`on_completed_callback` "only once, only on success" contract — a child's `on_completed_callback` never fires from `restore_initial()`/reversal, only from `advance()` reporting `true` or from `force_complete()`. This is independent of, and additional to, the root motion's own callbacks — setting `.on_started()` on the composite itself (after `.then()`/`.with()`) is unaffected and still fires exactly as before.

**Per-child delay inside `.with()` (phase-15).** `AnimaMotion.delay` previously did nothing on a child folded into an `_AnimaParallel` — only `_AnimaSequence` (via `compute_schedule()`) and the playback root ever consulted it, so `Anima.on(a)....with_delay(3)` used *before* `.with(...)` combined it into a group silently dropped that delay once wrapped. `AnimaParallelInstance` now treats each child's own `delay` as an offset from the *parallel's own start* — not "after the previous child," since a parallel has no ordering for that to mean anything; `delay_basis` is not consulted here, only on an `_AnimaSequence` step. A child with `delay <= 0.0` (the default) still starts immediately, exactly as before. This is what makes a staggered `.with()` group behave as authored: `spiral.with_delay(3).with(overlay.with_delay(3.5))` starts `spiral` 3s after the group itself starts and `overlay` 0.5s after `spiral` — and, combined with the pre-existing `_AnimaSequence` behaviour, a `.then(parallel_group)` step where nothing set delay on the *group itself* starts that whole step the instant the previous step ends, with each child inside it then staggering from that same instant per its own `delay`.

V1's `loop_in_circle` family maps to `.repeat(count, alternate = true)` — confirmed against `addons/anima/core/anima_node.gd` in the v1 reference project: `LOOP_IN_CIRCLE` toggles its internal play mode between `NORMAL` and `BACKWARDS` every iteration, which is exactly `alternate`'s existing ping-pong. V1's `loop_backwards` family (every iteration reversed, not alternating) composes as `Anima.play_backwards(motion.repeat(count))` rather than needing a third mode — reversing an `_AnimaRepeat` already reverses its child once and keeps repeating that. V1's `play_as_backwards_when(when)` was itself just a branch over its own `play()`/`play_backwards()` equivalents (confirmed in the same v1 file), matching this phase's decision not to add a dedicated conditional-direction method.

Convenience duration resolves through a chain when omitted: an explicit `.with_duration()` call wins outright; otherwise the target's attached `AnimaBehaviour.default_duration` applies, when one is attached via `Anima.attach_behaviour()`; otherwise a new `Anima.default_duration` project-level constant applies. A motion-theme layer between those last two is deferred — `AnimaMotionTheme` doesn't exist yet — so the chain currently has three links, not four; adding the theme link later only inserts a step, it doesn't change this contract. The resolved value is read live at motion-start each time, never copied into the motion early, so a later default change still applies.

`.property_by(path: NodePath, delta: Variant, duration: float = 0.0)` joins `AnimaOnMotionFactory` alongside `.property()`, setting `is_relative = true` the same way `.move_by()`/`.rotate_by()`/`.scale_by()` already do.

Immediate backward playback is a new entry point, not an extension of `AnimaPlayback.reverse()` (which requires a prior captured run — see §Key technical decisions). `Anima.play_backwards(motion, target = null) -> AnimaPlayback` mirrors `Anima.play()` but builds the reversed instance immediately, before the first frame, using the same `AnimaMotionInstance.build_reversed()` every motion kind already implements. A condition-driven choice between the two (v1's `play_as_backwards_when`) is ordinary branching over these two calls; no dedicated third method is added for it.

`AnimaPlayback.pause()`, `.resume()`, and `.cancel()` are already motion-agnostic — they operate on playback `state`, not on `AnimaGroupMotion` specifically — so a convenience-created single motion is already stoppable exactly like a group or Grid motion; item 13 requires no new interruption mechanism. Reversal was the one capability that stayed group-only: this phase extends `AnimaPlayback.reverse()` (see Key technical decisions) to cover a leaf/composite target-bound motion too, so stop and reverse behave the same way across single, group, and Grid motion, per Exit Criteria 1.

A resource intended for serialization must hold an `AnimaTargetReference`. A transient direct target may be used for immediate playback only; saving cannot silently serialize that live object. The Composer displays the semantic name alongside the canonical property path and edits the canonical resource directly; its generic-property view additionally offers a searchable target-property list with type, current value, and validation feedback for `.property()` motions.

## Convenience method interface

| Surface | Exact operation | Inputs & defaults | Result / failure | Canonical mapping |

## Convenience performance budget

`CONVENIENCE_BENCHMARK_SAMPLE_COUNT` is 10,000 equivalent motion creations per measured run. `CONVENIENCE_BENCHMARK_WARMUP_RUNS` is 3 and `CONVENIENCE_BENCHMARK_MEASURED_RUNS` is 5. The median convenience-factory creation time for each supported semantic motion must be no more than 50% above the median time for creating its equivalent canonical property motion; this ratio is `CONVENIENCE_CREATION_OVERHEAD_MAX`.

⚠️ Note: `CONVENIENCE_CREATION_OVERHEAD_MAX` was provisionally 10% before implementation. `tests/Anima.integration.convenience-parity.test.gd` measures each factory call against a reused factory (matching "no playback-state allocation" — the factory itself is built once, not per call). Measured against that fair baseline, the two `metadata` dictionary writes the Composer's semantic-name display (§Motion Composer shell) needs cost ~9.5% alone; target-class validation adds more on top, and `.size()`/`.position()`'s extra container/anchor ownership check (§Target-bound authoring contract's layout-warning behaviour) is the most expensive path, measuring ~35-40% over canonical on this machine. 10% was unreachable without dropping validation, the layout warning, or the Composer metadata — all already-specified requirements. 50% keeps headroom above the measured worst case for CI variance; it is a budget against runaway regressions, not a target every method is expected to sit near.

The benchmark measures construction only, not rendering or playback. Convenience-created motions use the normal evaluator and introduce no per-frame convenience-layer work; compilation, reversal, and interruption remain parity checks rather than separate performance paths.

## Playback lifecycle: cancel, complete, revert, reverse

`AnimaPlayback` already has `cancel()` (state → `CANCELLED`, `finished.emit(false)`) and `reverse()` (rebuilds/replays as documented in §Key technical decisions). This phase adds two new methods and a value-policy layer both existing and new methods read.

`AnimaMotion.CancellationValuePolicy { KEEP_CURRENT, RESTORE_INITIAL, COMPLETE }` (default `KEEP_CURRENT`) and `AnimaMotion.CompletionValuePolicy { KEEP_FINAL, RESTORE_INITIAL }` (default `KEEP_FINAL`) are new enums on `AnimaMotion`, unrelated to the existing `AnimaGroupMotion.CompletionPolicy` / `_AnimaParallel.CompletionPolicy` (which decide *when* a composite counts as done — `ALL_ITEMS`/`ALL_CHILDREN` etc. — not what value is left behind). The two concepts share the word "completion" but not a field or an enum.

- **`complete() -> void`** — new. Forces immediate arrival at `State.FINISHED`: applies the motion's authored end value(s) to `target`, runs the same completion path `_advance()` already takes on a natural finish (`on_completed_callback`, then `finished.emit(true)`), then applies `completion_value_policy`. `KEEP_FINAL` (default) leaves the just-applied end value in place — this is today's implicit natural-finish behaviour, now also reachable on demand. `RESTORE_INITIAL` re-applies the pre-animation snapshot immediately after `finished(true)` fires, for a "preview and revert" motion that must not visibly stay at its end state (e.g. a hover flourish). The policy applies identically whether `State.FINISHED` was reached naturally or forced via `complete()` — `complete()` is "arrive now," not a second, different outcome.
- **`revert() -> void`** — new. Unconditionally restores the pre-animation snapshot to `target` and stops playback: `state → CANCELLED`, `finished.emit(false)`. This is why reverse and revert are not equivalent (per the item's own wording): `reverse()` keeps playback running, now backward, from wherever it was; `revert()` stops it and snaps to the start. Callable from any `State.PLAYING`/`PAUSED` state; a no-op past `FINISHED`/`CANCELLED`.
- **`cancel()`** — unchanged signature, now reads `cancellation_value_policy`. `KEEP_CURRENT` (default) leaves whatever value was showing at the moment of cancellation — today's actual behaviour (playback simply stops advancing), so the default introduces no regression. `RESTORE_INITIAL` re-applies the pre-animation snapshot before `finished.emit(false)`. `COMPLETE` applies the motion's authored end value(s) — same value `complete()` would produce — but still emits `finished(false)`, never `on_completed_callback`/`finished(true)`: `COMPLETE` changes the *value* cancellation leaves behind, not the fact that it was a cancellation. This preserves the existing invariant that `on_completed_callback` and `success = true` only ever come from a genuine finish (see §Target-bound authoring contract).

**Pre-animation snapshot.** No new capture mechanism is introduced. Every motion-instance type already resolves and retains an observed start value when `from_value` is unset (`CURRENT_AT_MOTION_START`, see §Target-bound authoring contract) — that existing captured value *is* the pre-animation snapshot. Each instance type gains one new method, `restore_initial(target: Node) -> void`, alongside its existing `advance()`/`build_reversed()`, applying that same already-captured value back to `target`. A composite (`_AnimaSequence`/`_AnimaParallel`/`_AnimaRepeat`/`AnimaGroupPlayback`) delegates to each started child's own `restore_initial()`, the same top-down delegation `build_reversed()` already uses.

⚠ Verify: `AnimaGroupMotion`'s per-item `completion_value_policy`/`cancellation_value_policy` — this phase reads the policy off the *top-level* motion only (see §Speed, direction, and reduced motion for why fields are root-consulted this phase); an individual group item cannot currently override its own value policy. Flag if per-item override turns out to matter before groups commonly need it.

Cancellation cleanup beyond state + value policy is scoped to what the runtime actually owns today: state transition, the value policy above, and removal from `AnimaRuntime.active_playbacks` (already automatic — see §Lifecycle-safe playback policies). "Disconnect signals," "release property ownership," and "release layout overlays" from the item's fuller PRD wording have no corresponding mechanism yet — per-property ownership tracking, signal-wait leaves, and layout overlays are each their own un-shipped backlog item. Cleanup grows to cover them when those items ship, not speculatively now.

## Speed, direction, and reduced motion

Effective speed composes multiplicatively from four of PRD5's five named levels: **playback** (`AnimaPlayback.speed_scale`, existing) × **parent/local motion** (`AnimaMotion.speed`, existing — already composes across nesting today: `AnimaGroupPlayback.advance()` multiplies the delta it received by `group.speed` before handing it to each item's own `advance()`, so a group inside a group already composes correctly) × **direction** (new, below). The fifth level, "scope speed," names no concrete mechanism anywhere else in the current spec or backlog (no project/global speed constant exists); it is omitted rather than invented, per the item's own "implementations may simplify how many levels are exposed initially" allowance.

**Direction: `forward_speed` / `reverse_speed`.** `AnimaMotion` gains `forward_speed: float = 1.0` and `reverse_speed: float = 1.0`, independent of the existing `speed` (which keeps meaning "the general multiplier PRD5 calls `.speed()`, applied regardless of direction"). `AnimaPlayback` gains `_is_reversed: bool = false`, set `true` in `_init()` when `p_start_reversed`, flipped on every successful `reverse()` — repeated direction changes stay correct since it's a flip, not a one-time set. `AnimaMotion.build_reversed()` implementations already carry `forward_speed`/`reverse_speed` through unchanged (they copy fields the same way they already copy `speed`/`delay`), so reading `motion.reverse_speed` after a swap-to-reversed-motion still reflects the originally authored value.

`AnimaPlayback._advance()` computes the top-level multiplier once: `speed_scale * (motion.reverse_speed if _is_reversed else motion.forward_speed)`, applied to `delta` before it reaches `_instance.advance()` — the same point `speed_scale` alone is applied today. `AnimaMotion.speed` and any nested `group.speed` continue composing exactly as they do today, deeper in the existing call chain (`AnimaGroupPlayback.advance()`, `AnimaPropertyMotionInstance.advance()`). Net effect: `speed_scale × direction_speed × (each level's own .speed as the delta is traversed)` — Group speed scaling and Nested speed multiplier composition are therefore already-correct existing behaviour once the direction term is added; no per-level rework is needed for those two items.

`forward_speed`/`reverse_speed` are consulted only for the playback's own root motion, each time direction changes at the root — not re-consulted separately for a nested descendant motion, even though the fields exist on every `AnimaMotion` (so a motion played standalone later still has its own values available). This is the "implementations may simplify how many levels are exposed initially" allowance the item text grants; nested per-motion direction speed is deferred, not designed out.

**Spring simulation speed scaling.** `AnimaPropertyMotionInstance._advance_spring()` (`addons/anima/motion/runtime/anima_property_motion_instance.gd`) currently scales `_elapsed` by `motion.speed` but integrates `_spring_velocity`/`_spring_value` with the raw, unscaled `delta` — so today, `speed`/`speed_scale` visibly change *when* a spring is considered settled without changing how fast it visually moves, which is the gap this item names. Fix: compute `var scaled_delta := delta * motion.speed` once at the top of `_advance_spring()` and use `scaled_delta` for both `_elapsed` accumulation and the semi-implicit Euler step (`_spring_velocity += acceleration * scaled_delta; _spring_value += _spring_velocity * scaled_delta`); `delta` (already `speed_scale`- and direction-scaled by the time it reaches here) is never used unscaled again. Physical retargeting (`retarget()`/`retarget_spring()`) is unaffected — it changes the target value, not the delta the simulation steps by.

**Manual stepping.** `AnimaPlayback._advance(delta)` is currently private-by-convention (leading underscore) and the only per-frame entry point, called solely by `AnimaRuntime._process()`. This phase adds a public `step(delta: float) -> void` wrapper (`func step(delta: float) -> void: _advance(delta)`) — the direct-drive entry point the item requires — with no separate clock-mode selection (`AnimaClock` PROCESS/PHYSICS/UNSCALED/MANUAL stays out of scope; see the phase brief's Not This Phase). Effective speed applies automatically since `_advance()` already computes it; `step()` adds no separate scaling of its own. A caller drives a playback manually today only by constructing `AnimaPlayback` directly (bypassing `AnimaRuntime`, `_runtime` stays `null`) and calling `step()` each tick itself.

**Reduced-motion override.** `Anima` (the existing static facade — see `Anima.default_duration` in §Target-bound authoring contract) gains `static var reduced_motion: bool = false` — the single global switch (user decision: "Only `Anima.reduced_motion` is global … and supersedes any speed chosen"). `AnimaMotion.reduced_motion_speed: float = -1.0` is a per-motion sentinel field (`< 0.0` means "no override") — the per-animation speed control the same decision asked for ("I want to be able to control the speed of the single animation"). Whether the override is *active* for a given playback reconciles with the existing `AnimaBehaviour.ReducedMotion { SYSTEM, ENABLED, DISABLED }` (`anima_behaviour.gd`), discovered during implementation: that enum's own doc comment already anticipates this exact gap — "`SYSTEM` and `DISABLED` retain the authored group timing until a system-preference adapter is introduced." `Anima.reduced_motion` **is** that adapter, not a second, competing mechanism:

- `target`'s attached `AnimaBehaviour.reduced_motion == ENABLED` → reduced treatment is active regardless of `Anima.reduced_motion`.
- `== DISABLED` → never active, regardless of `Anima.reduced_motion`.
- `== SYSTEM` (the default), or no `AnimaBehaviour` attached at all → active exactly when `Anima.reduced_motion` is `true`.

When active and `reduced_motion_speed > 0.0`, `_advance()` uses that value as the effective speed outright, replacing the `speed_scale × direction_speed` product for that frame (motion-level `.speed` still applies underneath it, same as any other effective-speed consumer) — superseding whatever speed was otherwise chosen, per the decision. When active but no `reduced_motion_speed` is set (still `< 0.0`), nothing changes.

**`reduced_motion_speed == 0.0` means complete immediately, not "freeze forever."** A literal `0.0` multiplier would never advance the motion at all — the opposite of a reduced-motion outcome — so `_advance()` special-cases the exact value `0.0` as a sentinel: when active and `reduced_motion_speed == 0.0`, it calls `complete()` on itself instead of scaling the frame's delta, and returns. This reuses `complete()`'s own value-policy handling and callback/signal contract as-is — no new field, no new behaviour needed beyond what §Playback lifecycle already defines. This is the web's `prefers-reduced-motion` sense of the term (remove the motion, don't just slow it down) and is also literally what this phase's own brief already scoped: Exit Criteria always said "an override-eligible motion completes immediately **or** applies its reduced-motion speed" — both outcomes were approved from the start, this just makes both reachable through the one field instead of only the speed one. Swapping to an entirely different, simpler motion and removing group stagger stay deferred with the fuller per-motion policy (`FULL`/`SHORTEN`/`SIMPLIFY`/`COMPLETE_IMMEDIATELY`), still backlogged.

`AnimaGroupPlayback._uses_reduced_motion()` (which already exists and currently only checks `ENABLED`) extends to the same three-way resolution above, so a `SYSTEM`-default group also skips staggering once `Anima.reduced_motion` is globally on — closing the exact gap its own doc comment named, not a new behaviour.

## Lifecycle-safe playback policies

Of PRD5's six recommended defaults, five already hold today with no code change, and are recorded here as pinned decisions rather than left implicit:

- **Target hidden → continue.** Nothing reads `target.visible`; playback keeps advancing and writing values regardless.
- **Scene tree paused → follow selected clock.** `AnimaRuntime` is a plain `Node` with the default `process_mode` (`PROCESS_MODE_INHERIT`); Godot already stops calling `_process()` while the tree is paused, and resumes it automatically on unpause. This already matches PRD5's own recommended default clock (`PROCESS`) with zero Anima-specific code — pinned here, not reimplemented.
- **Target reparented → continue if references remain valid.** `target` is a plain `Node` reference; reparenting doesn't invalidate it, so `set_indexed()` calls keep landing on the same node regardless of its place in the tree.
- **Playback root freed → cancel whole playback.** `AnimaPlayback` is `RefCounted`; once nothing holds a reference to it (including `AnimaRuntime.active_playbacks`, which drops it on `finished`), it frees itself — there is no separate "root" object to leak.
- **Layout target removed → follow layout-exit policy.** Deferred — layout transitions don't exist yet (see the phase brief's Not This Phase).

**Target freed → cancel affected motion safely** is the one case with no existing mechanism, and the one this phase actually implements: it is the same failure class the Phase 10 review flagged as a leak (a discarded-but-uncancelled playback still sitting in `active_playbacks`, being advanced against a target that's gone). Replacing on-target-freed detection with `target.tree_exiting` (the originally specced mechanism) was rejected during implementation — it also fires on an ordinary reparent, which must *not* cancel. `AnimaPlayback._advance()` instead checks `is_instance_valid(target)` each frame (gated behind `_has_target`, captured once at construction — see §Node liveness below) and calls `cancel()` the moment it's false, mirroring the same per-item check `AnimaGroupPlayback` already used.

**Node liveness: `is_instance_valid()`, never `!= null`.** A freed, non-`RefCounted` `Object` still compares equal to `null` via `==`/`!=` in this engine version, so a plain `target != null` guard silently stops distinguishing "never had a target" from "had one, now freed" — exactly the gap that let the freed-target case above go undetected until `_has_target: bool` (captured once at construction, while the reference is still known-good) was introduced as the reliable signal instead. See `project-rules.md` §Node Liveness for the general rule this incident produced.

## Grid motion contract

Grid motion is the grid-specialised group resource, not an independent playback system. It applies the shared item motion to the resolved grid cells and derives stagger ranks from `start_point` and one selected `distance_formula`. It uses the existing group distribution for delay and the existing execution record for replay, inspection, reversal, and compilation.

| Formula | Rank / traversal semantics |
|---|---|
| `EUCLIDEAN` | Straight-line distance from the start point. |
| `MANHATTAN` | Horizontal plus vertical distance. |
| `CHEBYSHEV` | The larger horizontal or vertical distance. |
| `ROW` / `COLUMN` | Distance along the corresponding axis. |
| `DIAGONAL` | Difference along the main diagonal. |
| `ANTI_DIAGONAL` | `abs((row + column) - (start_row + start_column))`. |
| `CLOCKWISE` / `ANTICLOCKWISE` | Polar-angle waves around the start point, with 12 o’clock as angle zero; cells sharing an angle share a wave. |
| `SPIRAL_INWARD` | The classic "spiral matrix" order: peels `grid_dimensions`'s own rectangle inward from its top-left corner, one ring at a time (top row, right column, bottom row, left column, next ring in). |
| `SPIRAL_OUTWARD` | `SPIRAL_INWARD`'s path in reverse — starts at the centre-most cell, expands outward, ends at the corner `SPIRAL_INWARD` starts from. |
| `SERPENTINE_ROW` / `SERPENTINE_COLUMN` | Alternating row-wise or column-wise traversal, reversing direction on each successive line. |

Clockwise and anticlockwise treat `start_point` as the centre. Their 12-o’clock origin is owned by the Grid motion contract, not by a playground. Grid rank ties are intentional simultaneous waves; the existing distribution determines their shared delay. `SPIRAL_INWARD`/`SPIRAL_OUTWARD` and `SERPENTINE_ROW`/`SERPENTINE_COLUMN` are the exceptions on both counts: each is a strict cell-by-cell traversal (no simultaneous waves) traced from the grid's own rectangle, not from `start_point` — a shape-preserving spiral or a boustrophedon reading order doesn't have a natural arbitrary-origin reading, and an angle-from-an-interior-point spiral stops looking like a spiral the moment it reaches that point's own edge (`SPIRAL_INWARD`'s original design, corrected after it shipped looking wrong in the showcase). `CLOCKWISE`/`ANTICLOCKWISE` are unaffected — they keep their `start_point`-centred polar-angle wave.

`AnimaGridMotion` defaults its inherited `order.kind` to `GRID` in its constructor — the same trigger `AnimaGroupScheduler` already used for the existing (Euclidean-only, virtual-grid) `GRID` order kind, now upgraded: when the group is actually an `AnimaGridMotion`, that kind ranks through `distance_formula` and the grid's own `grid_dimensions`/`start_point` instead. A plain `AnimaGroupMotion` still authored with `order.kind = GRID` keeps the original virtual-grid behaviour untouched. An author can still set `order.kind` to `FORWARD`/`REVERSE`/`CENTRED`/`RANDOM` (Top/Bottom/Center/Random) directly on an `AnimaGridMotion` to fall back to the same flat-list ordering any other group has — `distance_formula` is only consulted while `order.kind` stays `GRID`.

**Nesting a group or grid as another group's item motion.** `AnimaGroupMotion.item_motion` is typed `AnimaMotion`, not restricted to a leaf property motion — an `AnimaGroupMotion`/`AnimaGridMotion` composes as a shared item template exactly like any other motion kind already does inside `_AnimaSequence`/`_AnimaParallel`. `AnimaGroupPlayback` already creates one independent runtime instance of `item_motion` per resolved item and advances it with that item's own resolved node as `target` — the same per-item target-passing `Anima.item()`'s `PLAYBACK_CONTEXT` resolution already relies on. Because `AnimaTargetCollection.Kind.CHILDREN`/`DESCENDANTS` resolve against whichever node is passed to a group at `advance()` time, not a node fixed at authoring time, a nested `item_motion` using `CHILDREN` resolution genuinely resolves each outer item's own distinct children at runtime. A grid of grids therefore needs no new resolution mode, scheduling mechanism, or motion subtype — and it doesn't conflict with groups applying one item motion template (§Out of Scope): every outer item still runs the identical nested motion resource, each independently resolving its own target's children.

## Grid convenience shorthand

`Anima.grid(container: Node, grid_size: Variant = null) -> AnimaGridMotionFactory` mirrors `Anima.on(target)`'s ergonomics for the one motion kind `Anima.on()` doesn't cover. `AnimaGridMotionFactory` is a lightweight `RefCounted` under `motion/runtime/`, the same category as `AnimaOnMotionFactory`/`AnimaItemMotionFactory`, storing `container` and an internal `AnimaGridMotion` whose `target_collection.kind` is set to `CHILDREN` against `container`. Most fields keep `AnimaGridMotion`'s own existing constructor default (`grid_dimensions = Vector2i(1, 1)` with its existing `GridContainer`-column inference when left unset, `spiral_direction = CLOCKWISE`) — the factory doesn't re-decide defaults `AnimaGridMotion` already owns, with one deliberate exception: `_init()` also sets `distance_formula = DistanceFormula.EUCLIDEAN`, a *factory-level* default distinct from `AnimaGridMotion`'s own general-purpose `ROW` default, which stays unchanged for hand-built usage — the shorthand's own common case is "radiate from a point," not "sweep row by row." `AnimaGroupDistribution.stagger_interval` already defaults to `0.05` on the resource itself, so the factory doesn't need its own override for that one. `_init()` itself leaves `item_motion` unset, same as before — the default `item_motion` below is a distance-formula-preset-only convenience, not a construction-time one.

**Default `item_motion` — preset methods only.** Each of the 13 distance-formula preset methods (`.radial()`, `.diamond()`, `.box()`, `.by_row()`, `.by_column()`, `.diagonal()`, `.anti_diagonal()`, `.clockwise()`, `.counter_clockwise()`, `.spiral_in()`, `.spiral_out()`, `.serpentine_row()`, `.serpentine_column()` — §below) also ensures `item_motion` is set: if `item_motion` is still `null` at the moment the preset runs, it calls `keyframes(DEFAULT_ITEM_MOTION, DEFAULT_DURATION).with_ease(DEFAULT_EASE)` (the same `.keyframes()`/`.with_ease()` described below) before setting `distance_formula`. This is deliberately narrower than a construction-time default: calling `Anima.grid(container)` alone, or reaching `.play()` through `.with_distance_formula(...)` directly rather than a named preset, still requires an explicit `.with_item_motion()`/`.keyframes()` call, unchanged from before this addition — only the named one-liner preset methods get a free, playable default motion, since those are the ones meant to work as a single fluent statement with nothing else supplied. All three defaults are named constants on `AnimaGridMotionFactory`, not inline literals:

```gdscript
const DEFAULT_DURATION := 0.3
const DEFAULT_EASE := AnimaEase.Kind.EASE_IN_OUT
const DEFAULT_ITEM_MOTION := {
	"from": {"opacity": 0.0, "scale": AnimaValue.target(NodePath("scale")).subtract(Vector2(0.25, 0.25))},
	50: {"scale": AnimaValue.target(NodePath("scale")).add(Vector2(0.15, 0.15))},
	"to": {"opacity": 1.0, "scale": AnimaValue.target(NodePath("scale"))},
}
```

A fade-in from 0 opacity that pulses each item's own scale 0.25 down at rest, 0.15 up at the midpoint, back to its own resting scale — `AnimaValue.target(NodePath("scale"))` resolves per item against each item's own current scale (§Dynamic values), the same mechanism `examples/showcase/grid/inventory_grid.gd` already hand-authors this exact shape with. `DEFAULT_EASE` is scoped to this preset-only default `item_motion` — it does not change `AnimaKeyframeMotion.default_ease`'s own general `Kind.LINEAR` default (§Keyframe motions), the same "factory-level convenience, underlying resource's own default stays untouched" pattern `distance_formula`'s `EUCLIDEAN` default already established. Setting `item_motion` explicitly *before* calling a preset (`.keyframes({...}).diagonal()`) means the preset's own `null` check finds it already set and leaves it alone — the default never overwrites a caller's own choice, only fills a genuine gap. Calling `.with_item_motion(...)`, `.keyframes(...)`, or `.with_ease(...)` *after* a preset still simply overwrites whatever's there, default or not, the same as any other chain call. `.with_duration()`/`.with_ease()`/`.with_pivot()`/`.play()`'s existing "no `item_motion` set" error paths (§below) are unaffected — they still trigger normally whenever no preset method supplied the default and nothing else set one either.

**`grid_size` — accepted types and resolution.** GDScript has no union parameter types, so `grid_size` is typed `Variant`; `_init()` dispatches on `typeof(grid_size)` and always finishes by calling the same dimension-setting path `.with_dimensions()` uses (§below), so a value supplied here auto-derives a centred `start_point` exactly like calling `.with_dimensions()` explicitly would, and a later explicit `.with_start_point()` still overrides it regardless of order (unchanged from the existing contract).

- `Vector2i` — used directly as `grid_dimensions`.
- `Vector2` — converted with `Vector2i(floori(value.x), floori(value.y))`, the same "whole cells only, never round up past what fits" floor convention `inventory_grid.gd`'s own `_fit_count()` already uses for fractional-fit math. ⚠️ Note: a minor, low-stakes convention call, not a value any other artifact already owns — flagged for sanity-check, not blocking.
- `Node` — infers dimensions from that node (see below), instead of from `container`.
- `null` (the default, i.e. omitted) — infers dimensions from `container` itself.
- Any other type — reports an error naming the invalid type and falls back to the same inference path as `null`, the same "report loudly, don't invent a value, but don't halt the chain either" posture `.with_duration()`/`.with_ease()`/`.with_pivot()` already use for their own invalid-state cases.

**Inference** (`null` case, or an explicit `Node`) resolves against the reference node (`container` or the given `Node`) with the *child count always read from `container`*, never from the reference node when the two differ:

1. The reference node exposes both a `rows` and a `columns` property (`"rows" in node and "columns" in node`) → `grid_dimensions = Vector2i(node.columns, node.rows)`.
2. Else the reference node exposes a `columns` property alone (`"columns" in node`) — true for any real `GridContainer`, and for any custom node that happens to expose the same property name → `columns = node.columns`; `rows = ceili(container.get_child_count() / float(columns))`.
3. Else (no usable property found) → `columns = 1`; `rows = container.get_child_count()`.

`.with_dimensions(value: Vector2i) -> AnimaGridMotionFactory` also auto-derives a centred `start_point` — `Vector2i(floori(value.x / 2.0), floori(value.y / 2.0))` — **unless** `.with_start_point()` has already been called explicitly on this factory, tracked by a private `_start_point_explicit: bool` flag `.with_start_point()` sets. Floored, not rounded or truncated toward zero on a negative axis, so an odd dimension (e.g. `5`) centres on index `2`, matching "the middle tile," not index-2.5 rounded up to 3. Calling `.with_dimensions()` more than once re-derives the centre each time from whatever the latest dimensions are, still only when no explicit start point exists yet. Calling `.with_start_point()` *before* `.with_dimensions()` is also respected — the flag is checked, not just chain order — so an explicit choice is never silently overwritten regardless of which call comes first.

A single `AnimaGridMotion` is the only resource kind this shorthand ever builds, so — unlike `Anima.on()`, which needs a factory because one target maps to many possible property-motion kinds — no per-property dispatch is needed; the factory exists purely to keep `container` in scope across the chain. Chain methods mutate the internal motion and return the factory itself (not the motion), so `.play()` stays reachable at the end of the chain: `.with_item_motion(motion)`, `.with_dimensions(value: Vector2i)`, `.with_distance_formula(value: AnimaGridMotion.DistanceFormula)`, `.with_start_point(value: Vector2i)`, `.with_stagger_interval(value: float)` (sets `distribution.stagger_interval`). A `.motion -> AnimaGridMotion` getter exposes the raw resource for anyone who wants to save it or hand it to `Anima.play()` with a different target instead of playing immediately.

`.keyframes(initial: Dictionary = {}, duration: float = 0.0) -> AnimaGridMotionFactory` is the same name as `AnimaOnMotionFactory.keyframes()` (§Keyframe interface) — deliberately, so authoring a keyframed item motion reads identically whichever factory it's on — but a deliberately different return: `AnimaOnMotionFactory.keyframes()` returns the built `AnimaKeyframeMotion` itself (nothing else needs to chain after it, since `Anima.on()` plays a single target directly), while this one builds the same `Motion.keyframes(initial)` motion, sets its `duration`, assigns it as `item_motion` (equivalent to `.with_item_motion(...)`), and returns **the factory** — so `.play()` still stays reachable at the end of the chain, matching every other `AnimaGridMotionFactory` chain method's own contract. `Anima.on(target).keyframes(...)` is unchanged by this addition.

`.play() -> AnimaPlayback` calls `Anima.play(_motion, container)` using the factory's own stored `container`, closing the "hand-build a target collection and call `Anima.play()` yourself" gap the backlog item names. Mirroring `Anima.on(null)`'s existing behaviour, `.play()` with no `item_motion` ever set — no preset method called, and no explicit `.with_item_motion()`/`.keyframes()` either — reports an error and returns `null` rather than playing an empty grid.

**`.then()`/`.with()` (phase-15).** `_init()` also sets `motion.convenience_target = container` — the same `AnimaMotion.convenience_target` field `Anima.on(target)`-built motions carry (§Target-bound authoring contract) — so an `AnimaGridMotion` built through this factory participates in the same `.then()`/`.with()`/`.play()` machinery as any `Anima.on()` motion, and composes correctly (per-leaf target resolution) when combined with one. `AnimaGridMotionFactory.then(other: Variant) -> AnimaMotion` / `.with(other: Variant) -> AnimaMotion` delegate directly to `_motion.then(other)` / `_motion.with(other)` (`AnimaMotion`'s own chain methods, including their factory-unwrapping resolution — "Chaining a motion factory directly" above) and return **the resulting composite motion**, not the factory — chaining a grid motion into a sequence/parallel group is combining it with something else, the same reason `AnimaOnMotionFactory`'s semantic methods return the built motion rather than the factory once nothing else needs to configure this specific grid. `Anima.grid(container).radial().then(Anima.on(other_node).fade_out(0.3)).play()` and `Anima.grid(a).radial().with(Anima.grid(b).diagonal())` are both valid — the second passes a raw `AnimaGridMotionFactory` as `other`, resolved via its own `.motion` property with no `.motion`/`.play()` unwrapping needed at the call site. Calling `.then()`/`.with()` before any `item_motion` is set is not blocked here (unlike `.play()`) — the resulting composite still requires an `item_motion` before *it* plays, surfacing the same existing "no item_motion" error at that point.

`.with_duration(value: float) -> AnimaGridMotionFactory`, `.with_ease(value: Variant) -> AnimaGridMotionFactory`, and `.with_pivot(value: AnimaPivot.Kind) -> AnimaGridMotionFactory` reach into whatever `item_motion` is already set — built by `.keyframes(...)` or supplied to `.with_item_motion(...)` — and set its `duration`/`ease`/`pivot` (`AnimaPropertyMotion`) or `duration`/`default_ease`/`default_pivot` (`AnimaKeyframeMotion`) directly, then return the factory. `.with_ease()`'s `value` runs through `AnimaEase.from(value)` first (§Easing curve library), so a bare `AnimaEase.Kind` works directly — `Anima.grid(container).keyframes({...}).with_duration(0.3).with_ease(AnimaEase.Kind.EASE_IN_OUT).play()` — with no separate `AnimaEase.new()`/`kind =` preamble needed for the common named-curve case. These exist specifically so a keyframed grid item motion can be fully authored, including its easing and pivot, in one fluent statement, the same way `.with_duration()`/`.with_ease()`/`.with_pivot()` already chain directly onto `AnimaOnMotionFactory.keyframes()`'s own returned motion (§Keyframe interface), without a factory indirection in between. Calling any of the three before any `item_motion` exists, or when `item_motion` is a composite with no matching field of its own (`_AnimaSequence`, `_AnimaParallel`, and similar), reports an error naming which case it was and leaves the factory unchanged (no crash, no silent no-op) — the same "report loudly, don't invent a value" posture `.play()`'s own missing-`item_motion` check already uses.

**Distance-formula presets.** Each preset method is pure sugar for `.with_distance_formula(DistanceFormula.X)` — sets that one field and returns the factory, identical contract to calling `.with_distance_formula()` directly, so chain order relative to `.with_dimensions()`/`.with_start_point()` doesn't matter. One name per formula, no aliases — a second name for the same behaviour adds surface area without adding capability:

| `MANHATTAN` | `.diamond()` |
| `CHEBYSHEV` | `.box()` |

| `ANTI_DIAGONAL` | `.anti_diagonal()` |

`ROW`/`COLUMN` and `SERPENTINE_ROW`/`SERPENTINE_COLUMN` each read as a matched pair (`.by_row()`/`.by_column()`, `.serpentine_row()`/`.serpentine_column()`); `MANHATTAN`'s rings are diamonds (L1 distance) the same way `CHEBYSHEV`'s are squares (L∞ distance), so `.diamond()`/`.box()` name the shape each formula actually draws.

## Group convenience shorthand

`Anima.group(targets: Variant) -> AnimaGroupMotionFactory` mirrors `Anima.grid()`'s ergonomics for the general (non-grid) `Motion.group(target_collection, item_motion)` builder. `AnimaGroupMotionFactory` is a lightweight `RefCounted` under `motion/runtime/`, the same category as `AnimaOnMotionFactory`/`AnimaGridMotionFactory`, wrapping an internal `AnimaGroupMotion`. `targets` dispatches on `typeof(targets)`, the same pattern `Anima.grid()`'s `grid_size` already establishes:

- `Node` — `target_collection.kind = CHILDREN`, `target_collection` resolved against that node at play time (matching `Anima.grid(container)`); the factory stores it as its own `container` for `.play()`.
- `Array` — `target_collection.kind = EXPLICIT`, `target_collection.reference_data` set to the array's entries. Any entry that isn't a `Node` reports an error naming the invalid entry and is excluded, rather than failing the whole call — the same "report loudly, skip, don't halt the chain" posture `Anima.grid()`'s invalid-`grid_size`-type case already uses. The factory's own `container` stays `null` — `AnimaTargetCollection.EXPLICIT` resolves `reference_data`'s own live `Node` references directly and needs no root, the same way an already-shipped hand-built `EXPLICIT` group plays with `target = null` today.
- Any other type (`String`, `int`, `null`, …) — reports an error naming the invalid type and returns `null` immediately, mirroring `Anima.on(null)`'s existing fail-fast contract; unlike `grid_size`, there is no sensible inferred fallback for target identity itself.

`item_motion` is never a constructor argument — matching `Anima.grid()`'s own deferral, it's supplied via chain calls after construction: `.with_item_motion(motion: AnimaMotion) -> AnimaGroupMotionFactory` sets it directly; `.keyframes(initial: Dictionary = {}, duration: float = 0.0) -> AnimaGroupMotionFactory` builds a keyframe `item_motion` the identical way `AnimaGridMotionFactory.keyframes()` does (§Grid convenience shorthand) and returns the factory, not the built motion, for the same "`.play()` stays reachable at the end of the chain" reason. `.with_duration(value)`/`.with_ease(value)`/`.with_pivot(value)` reach into whatever `item_motion` is already set and apply the identical field-mapping and "no `item_motion`, or no matching field" error contract `AnimaGridMotionFactory`'s own three equivalents already define. `.with_delay(value: float)` sets `motion.delay` on the internal `AnimaGroupMotion` directly (root-level chain delay, §Key technical decisions), the same delegation `AnimaGridMotionFactory.with_delay()` already uses. `.on_started(callback)`/`.on_completed(callback)` delegate to the internal motion's own base `AnimaMotion` methods (§Convenience method interface) the same way. `.then(other)`/`.with(other)` delegate to `_motion.then(other)`/`_motion.with(other)` and return **the resulting composite motion**, not the factory — identical contract to `AnimaGridMotionFactory.then()`/`.with()` (§Grid convenience shorthand) — so `Anima.group(container).with_item_motion(m).then(Anima.on(other).fade_out())` and `Anima.group([a, b]).with_item_motion(m).with(Anima.grid(c).radial())` both compile and play with no `.motion`/`.play()` unwrapping needed. `.motion -> AnimaGroupMotion` exposes the raw resource, matching `AnimaGridMotionFactory.motion`. `.play() -> AnimaPlayback` calls `Anima.play(_motion, container)` (`container` is `null` for the `Array` form, per above); no `item_motion` ever set reports an error and returns `null`, the same missing-`item_motion` contract `AnimaGridMotionFactory.play()` already has.

No ordering, stagger, distribution, or filter sugar is added on top of what `AnimaGroupMotion`'s own fields (§Data model) already expose — `Anima.group()` exists to remove the "hand-build a target collection" step, not to add new group behaviour; an author who needs `order`/`distribution`/`filter` configuration beyond the two target-selection forms above still reaches `.motion` and sets those fields directly, same as any hand-built `AnimaGroupMotion` today.

## Keyframe motions

`AnimaKeyframeMotion` is a new leaf `AnimaMotion` subtype, parallel to `AnimaPropertyMotion` rather than a composite of several property motions — it advances every track together against one `_elapsed`/`duration` clock, the same single-instance shape every other leaf already uses. `duration: float = 0.0` resolves through the exact same chain `AnimaPropertyMotionInstance._resolve_duration()` already applies (explicit → `AnimaBehaviour.default_duration` → `Anima.default_duration`) when left at its default, and `ease: AnimaEase = AnimaEase.new()` is not present — segments use `default_ease: AnimaEase = AnimaEase.new()` instead (`Kind.LINEAR` by default, matching every other motion's own default), since a keyframe motion has many segments, not one.

**Authoring — two forms, one resource.** `Motion.keyframes(initial: Dictionary = {}) -> AnimaKeyframeMotion` and `AnimaOnMotionFactory.keyframes(initial: Dictionary = {}, duration: float = 0.0) -> AnimaKeyframeMotion` both parse `initial` (if non-empty) into canonical tracks immediately and return the same `AnimaKeyframeMotion`. `AnimaKeyframeMotion` gains a fluent `.at(offsets: Variant, values: Dictionary) -> AnimaKeyframeMotion` chain method (returns self) that merges one more offset declaration into the existing tracks — the incremental form `Motion.keyframes().at(["from", 10], {...}).at([23, 50], {...})` calls the identical merge path the dictionary form's parser uses per declaration, so both authoring surfaces are guaranteed to produce the same resource by construction, not by a separate equivalence check. `.duration(value)` is **not** exposed bare — it collides with the existing `duration` field name the same way `duration()`/`ease()`/`delay()` already do on `AnimaPropertyMotion` (§Convenience method interface), so keyframes follow the same established `.with_duration(value: float) -> AnimaKeyframeMotion` naming instead of the PRD's literal `.duration(...)` example. `.with_ease(value: Variant) -> AnimaKeyframeMotion` sets `default_ease` directly, for the same `with_`-prefix reason, and returns self — chaining onto whatever `.keyframes(...)` already returned, e.g. `Anima.on(target).keyframes({...}).with_duration(0.3).with_ease(AnimaEase.Kind.EASE_IN_OUT)`, with no `AnimaGridMotionFactory`-style factory indirection needed since `AnimaOnMotionFactory.keyframes()` already returns the motion itself. `value` runs through `AnimaEase.from(value)` (§Easing curve library) so a bare `AnimaEase.Kind` works without constructing an `AnimaEase` resource by hand.

**Offset resolution.** `"from"` → `0.0`, `"to"` → `1.0`, an `int`/`float` key is a percentage (`50` → `0.5`); any other key type is a validation error. A dictionary key may itself be an `Array` of such keys (grouped offsets, e.g. `["from", 10]: {...}`) — the same per-offset value dict applies to every resolved offset in the group, each producing its own `AnimaKeyframeStop`. Declaration order never determines playback order: every parse pass sorts each track's `stops` by `offset` after merging, so `{50: {...}, "from": {...}}` and `{"from": {...}, 50: {...}}` produce identical tracks.

**Multi-property stops and reserved keys.** A per-offset value dict's non-underscore keys are property declarations for that offset — a semantic name (`opacity`, `position`, `scale`, `rotation`, `color`, `size`, resolved to `modulate:a` / `position` / `scale` / `rotation` / `modulate` / `size` — the exact mapping §Convenience method interface's canonical-mapping column already uses) or an arbitrary `NodePath`-parseable property string used directly. Each declared property gets (or extends) its own `AnimaKeyframeTrack`, keyed by its resolved canonical `NodePath`. Underscore-prefixed keys are reserved metadata, stored on the `AnimaKeyframeStop` itself, never as a property: `_ease: AnimaEase` sets that stop's own easing (governing the segment *arriving* at it); `_pivot: AnimaPivot.Kind` declares a pivot inline with the stop it's most relevant to (phase-14 — see "Pivot" below); `_hold`, `_marker`, `_callback` remain reserved (not implemented this phase, parsing accepts and ignores them without error) so a future phase can add them without a breaking rename.

**Implicit initial value (v1 parity).** A track whose earliest declared stop is not at offset `0.0` is missing its starting value, not holding one deliberately — matching v1's own behaviour (`addons/anima/utils/tween_utils.gd` `calculate_dynamic_value`), parsing synthesises an offset-`0.0` stop for that track whose `value` is `AnimaValue.target(track.property_path)` (§Dynamic values) — the exact same "resolve this property's own live value on the target at motion start" primitive an author could write by hand, just inserted automatically. This runs once, during the same parse pass that sorts each track's `stops` — by the time `.validate()` or `AnimaKeyframeMotionInstance` ever sees the track, the synthesised stop is a completely ordinary `AnimaKeyframeStop`, indistinguishable from one the caller wrote themselves. No new resolution mechanism: `AnimaKeyframeMotionInstance` already resolves an `AnimaValue` found as a stop's `value` (§Dynamic values — `AnimaKeyframeStop.value` is one of the fields that already checks `is AnimaValue`), so evaluation, reversal, and the Composer's own inspection all handle it for free. The synthesised stop's `ease` stays unset (`null`) — nothing precedes offset `0.0`, so no segment ever arrives at it, the same reason an authored first stop's `ease` is already never consulted (§Reversal below). This only fires when a track has *no* stop at offset `0.0` at all; an author who writes an explicit `"from"` (or literal `0`) stop for a property is never overridden — the synthesis fills a genuine gap, it doesn't second-guess an authored value.

`Anima.on(top_node).keyframes({"to": {"scale": Vector2(2.0, 2.0), "opacity": 0}})` is now valid and animates both properties from `top_node`'s own live `scale`/`modulate:a` at motion start to the declared `"to"` values — previously this produced a single-stop track that just held `Vector2(2.0, 2.0)`/`0` for the whole motion with no interpolation, the exact gap this closes.

**Pivot.** `AnimaKeyframeMotion` gains `default_pivot: AnimaPivot.Kind = NONE`, and `.with_pivot(value: AnimaPivot.Kind) -> AnimaKeyframeMotion` sets it directly (same `with_`-prefix reason, same "returns self" contract as `.with_duration()`/`.with_ease()`) — a separate method from `.with_ease()`, not folded into it, since pivot and easing are unrelated settings that happen to share the same resolve-once timing. A stop's own `_pivot` (`AnimaKeyframeStop.pivot: Variant`, `null` when not declared — same nullable-sentinel shape `ease` already uses) is v1-parity authoring convenience, not a per-stop *effect*: pivot only makes sense as one fixed anchor for the whole transform, the same "resolved once" constraint `AnimaPropertyMotion.pivot` already has, so a mid-animation pivot change has no defined meaning and isn't supported. `AnimaKeyframeMotionInstance` resolves exactly one pivot value, once, at the same moment it resolves duration and dynamic values: scan `tracks` in order, and each track's `stops` in offset order, for the first non-`null` `_pivot`; fall back to `default_pivot` when none is declared anywhere. If the resolved pivot is `NONE`, or no track's canonical property is `scale`/`rotation`, nothing is applied — the same silent-no-op posture `AnimaPropertyMotion.pivot` already has. Otherwise it calls the same shared `_apply_pivot_to(target, pivot)` `AnimaPropertyMotionInstance` uses (§Motion pivot control).

**Evaluation.** `AnimaKeyframeMotionInstance.advance(target, delta)` resolves global progress `t` the same way `AnimaPropertyMotionInstance` does (`_elapsed / duration`, clamped to `[0, 1]`), then evaluates each track independently: find the bracketing pair of stops around `t` (before the first stop or after the last, clamp to that boundary stop's value — no extrapolation); compute the segment-local `u = (t - stop_a.offset) / (stop_b.offset - stop_a.offset)`; apply `(stop_b.ease or default_ease).evaluate(u)`; `lerp(stop_a.value, stop_b.value, eased_u)`; `target.set_indexed(track.property_path, result)`. A single-stop track is valid — it holds that value for the whole motion, no interpolation. Per the implicit-initial-value synthesis above, this now only happens when that one stop is itself at offset `0.0` (e.g. `{"from": {...}}` alone); any track whose earliest authored stop is later than `0.0` always ends up with at least two stops after parsing, never a held single value.

**Easing mirroring.** `AnimaEase` gains `func mirrored() -> AnimaEase`, returning a `duplicate()` of itself with `kind` swapped through a fixed `Kind → Kind` table (ported directly from Anima v1's own `get_mirrored_easing()`): `EASE_IN ↔ EASE_OUT`, and the same `_IN ↔ _OUT` swap for the `SINE`/`QUAD`/`CUBIC`/`QUART`/`QUINT`/`EXPO`/`CIRC`/`BACK`/`ELASTIC`/`BOUNCE` families. A kind with no table entry (`LINEAR`, every `EASE_IN_OUT_*` variant, and every parameterised family kind — `SPRING`, `CUBIC_BEZIER`, etc.) mirrors to itself unchanged; every other field (amplitude, period, overshoot, spring/bezier parameters) survives via `duplicate()`, only `kind` changes.

**Reversal (literal values only).** `AnimaKeyframeMotionInstance.build_reversed()` produces a new `AnimaKeyframeMotion` whose every stop's `offset` becomes `1.0 - offset` — but easing *ownership* also has to shift, not just mirror in place, because of the "a stop's `ease` governs the segment arriving at it" convention: reversing the segment `s_i → s_{i+1}` (originally eased by `s_{i+1}`'s effective easing) means, after reversal, the segment runs the other way, so the easing moves to the *new* arriving stop — which is `s_i`'s reversed counterpart. Concretely, per track: walk the original stops **in reverse order** (this already produces offset-ascending order once each is transformed, since `1 - x` reverses monotonic order) and build each new stop as `{ offset: 1.0 - s_i.offset, value: s_i.value, ease: mirrored(effective_ease(s_{i+1})) }`, where `effective_ease(stop) = stop.ease if stop.ease != null else default_ease`, and the new first stop (donor: the original's very last stop, which had nothing after it) gets `ease = null` — nothing arrives at the first stop, so it's never consulted. The reversed motion's own `default_ease` is `original.default_ease.mirrored()`, for any future stop that falls back to it. This closes "Backward playback for keyframe motions": keyframes implement the same `build_reversed()` contract every leaf type does, so `AnimaPlayback.reverse()`/`Anima.play_backwards()` already work for them with no special-casing in `AnimaPlayback` itself — and unlike a same-values-same-easing swap, the reversed motion's segments actually *feel* reversed, not just reordered.

⚠️ Note: `AnimaPropertyMotionInstance.build_reversed()` (existing, shipped) still carries its single `ease` through unchanged on reversal — it never mirrors. That's a real, separate fidelity gap this same `AnimaEase.mirrored()` utility could close, but it touches already-shipped reversal behaviour outside this phase's approved scope (keyframes only). Flagging it as a candidate backlog item rather than changing it here.

Speed, direction, and reduced-motion overrides need no keyframe-specific work: `AnimaKeyframeMotion` inherits `speed`/`forward_speed`/`reverse_speed`/`reduced_motion_speed` from `AnimaMotion` directly, and `AnimaPlayback._advance()` already scales `delta` before it ever reaches `AnimaKeyframeMotionInstance.advance()` — the instance just accumulates whatever `delta` it receives, the same as every other leaf.

`AnimaKeyframeMotion` implements the base contract explicitly (`project-rules.md` §Patterns): `estimate_duration()` returns `AnimaDuration.fixed(duration)` — the same pattern `AnimaPropertyMotion.estimate_duration()` already uses, including reporting `fixed(0.0)` verbatim when `duration` is still chain-resolved rather than explicit (an existing, accepted simplification, not a new one); `create_runtime()` returns `AnimaKeyframeMotionInstance.new(self)`; `validate()` requires at least one track with at least one stop, and flags any duplicate offset within the same track after parsing (two stops at the identical resolved offset on one property is an authoring error, not a silent last-write-wins).

## Dynamic values

`AnimaValue` (`extends Resource`) resolves against live playback state instead of holding a fixed literal: `func resolve(context: AnimaValueContext) -> Variant`, one method with an internal `match kind` — the same "one class, many `Kind` values" shape `AnimaEase.evaluate(t)` already established, not a subtype per source or operation. `AnimaPropertyMotion.from_value`/`to_value` and `AnimaKeyframeStop.value` are already loosely `Variant`-typed today, so accepting an `AnimaValue` in any of them needs no field-type change anywhere — confirmed against their current declarations. Each consuming instance type checks `value is AnimaValue` and calls `resolve()` when true, otherwise uses the literal exactly as it does today.

**Resolution timing.** No new timing field or policy this phase (the phase brief's Not This Phase excludes configurable timing). Every `AnimaValue`-typed `from_value`/`to_value`/keyframe-stop-`value` resolves exactly once, at the same "resolved once at motion start" point `CURRENT_AT_MOTION_START` already captures (§Target-bound authoring contract) — inside the owning instance's setup on its first `advance()`, before that value is used as `from`/`to`. This is v1's own behaviour (`calculate_dynamic_value` runs once, when `calculate_from_and_to` builds the tween), not a narrowing of it.

**`AnimaValueContext` and how it reaches an instance.** `create_runtime()` gains an optional parameter — `func create_runtime(context: AnimaValueContext = null) -> Variant` — a backward-compatible signature extension; every existing call site needs no change. A plain `Anima.play(motion, target)` passes no context, so the instance falls back to `AnimaValueContext.new()` with `target`/`root` both set to its own resolved target and every group/grid field left at its `-1`/`-1.0` sentinel. `AnimaGroupPlayback._start_item()` is the one caller that builds a populated context — `target` = that item's own resolved node, `root` = the node the group itself was played against (the container, never an individual item — this is the decision that resolves the phase brief's "what does root mean" open risk, and matches v1's own `_root_node` override defaulting to the animated node), and `group_index`/`group_count`/`group_normalised_index`/`grid_row`/`grid_column` read from the group's own `AnimaExecutionRecord` (already retained for reversal/inspection — no duplicate per-item tracking is added). `group_normalised_index = group_index / max(group_count - 1, 1)`. `grid_row`/`grid_column` populate only when the group is actually an `AnimaGridMotion`; they stay `-1` for a plain `AnimaGroupMotion`, including one using virtual `GRID` order.

**Sources** (static factory methods on `AnimaValue` itself — no separate builder class; the `Motion` builder's own unprefixed name is an explicitly non-repeatable one-off per `project-rules.md` §Naming, so dynamic-value construction stays on the prefixed type instead of a second unprefixed class): `AnimaValue.constant(v)` wraps a literal so it can serve as an arithmetic operand or root value. `AnimaValue.target(property: NodePath)` reads `context.target`'s own property — v1's `.`/self reference. `AnimaValue.node(path: NodePath, property: NodePath)` reads another node's property, resolved via `context.root.get_node(path)` — v1's arbitrary node-path reference. `AnimaValue.root(property: NodePath)` reads a property directly off `context.root` itself. `AnimaValue.context(key: String)` reads `context.context_data.get(key)` — `AnimaPlayback` gains an optional `context_data: Dictionary` field, set before `play()`, threaded into every context built for that playback tree. `AnimaValue.group_index()` / `.group_count()` / `.group_normalised_index()` / `.grid_row()` / `.grid_column()` read the matching `AnimaValueContext` field directly.

**Arithmetic composition.** `.add(other)`, `.subtract(other)`, `.multiply(other)`, `.divide(other)`, `.minimum(other)`, `.maximum(other)` each take `other: Variant` — a literal **or another `AnimaValue`** — this is the v1-parity requirement the "multiple property references" backlog item adds: a formula combining two independent property reads (e.g. one node's width plus another's height) needs one `AnimaValue` to accept another as its own operand, not just a literal. `.negative()` and `.absolute()` are unary. Every arithmetic method returns a **new** `AnimaValue` wrapping the operation — it never mutates `self` — because the same base `AnimaValue` is often reused as the root of several different expressions (`w.multiply(0.5)` and `w.multiply(2.0)` must not interfere with each other or with `w`); this is a deliberate contrast with `AnimaKeyframeMotion.at()`'s mutate-and-return-self, which is safe there only because a keyframe motion isn't reused as a sub-expression. Resolution applies Godot's own native `+`/`-`/`*`//` operators to the two resolved runtime values, so it works across whatever Variant types they actually resolve to (`float`, `Vector2`, `Vector3`, `Color`, …) with no per-type branching. `.clamp(min_v, max_v)` clamps the resolved value between the two operands (each a literal or `AnimaValue`) using Godot's own `clamp()`. `.map(in_min, in_max, out_min, out_max)` linearly remaps: `out_min + (raw - in_min) / (in_max - in_min) * (out_max - out_min)`. `.x()` / `.y()` / `.z()` / `.component(index)` extract one scalar component from a resolved vector-typed value; extracting a component from a resolved scalar fails validation.

**Callable fallback.** `AnimaValue.custom(callable: Callable)` stores `kind = CUSTOM` and the callable in `custom_callable`; `resolve()` calls `custom_callable.call(context)` and returns its result. Named `custom`, not the PRD's literal `call` — `AnimaValue extends Resource` inherits `Object.call(method, ...)`, so a same-named override fails to parse (`"call(StringName, ...) -> Variant"` signature mismatch), discovered during implementation. This is the v1-parity escape hatch for computations no structural operation above expresses (v1's formulas ran through Godot's full `Expression` parser, so arbitrary math — trig, `sqrt`, `pow`, … — was implicitly available; the structural methods above cover the common cases explicitly, `AnimaValue.custom()` covers everything else). Per the backlog item, a `CUSTOM`-kind value is runtime-only: potentially non-serialisable, non-compilable, and unavailable in editor preview — the Composer and the compile-eligibility check below both treat it the same as any other author-supplied callable already unavailable to them (`AnimaEase.Kind.CALLABLE` is the existing precedent for this same category of limitation).

**Compile-eligibility interaction.** `AnimaGroupCompiler.check_eligibility()` already requires `item_motion is AnimaPropertyMotion` (`Blocker.ITEM_MOTION_NOT_A_PROPERTY_MOTION`), which already excludes a keyframe-based item motion from compilation — no change needed there. This phase adds one more blocker checked only once that gate passes: `Blocker.DYNAMIC_VALUE`, set when `item_motion.from_value is AnimaValue or item_motion.to_value is AnimaValue` — "this item motion's value is resolved per-item at runtime; there's nothing fixed to bake into a native curve." Upholds the existing "compilation requires static deterministic resolution" decision (§Key technical decisions) the same way `RUNTIME_ONLY_TARGETS`/`LIVE_MEMBERSHIP` already do, rather than introducing a separate rule for this new source of runtime-only-ness.

## Motion Composer shell

The Motion Composer is an `EditorPlugin`-owned bottom-panel workspace, not an inspector-only custom control and not a separate asset format. It opens an authored `AnimaMotion` resource graph from the editor and maintains one `AnimaComposerSession` for that graph. The session has a root resource, a currently selected motion within that graph, an optional selected scene node used as the target-resolution and preview context, and an active `SETUP` or `INSPECTION` view. It opens from either an inspected `AnimaMotion` resource or, now, an "Anima" Inspector section on a plain node carrying one (see §Motion Composer entry point) — both paths call the same `open_motion()`.

The shell provides graph navigation and creation of a Group Motion in a compatible composite parent. It also opens a standalone Group Motion as the root graph. If no selected scene node is available, authored configuration remains editable while resolving and previewing report that their target context is missing. Setup and inspection are views of the same session and selected resource; returning between them never reconstructs or copies the Group Motion.

Composer edits mutate the authored Resource through Godot editor undo/redo, so code, the Inspector, and the Composer immediately observe the same value. Selection, active view, and preview playback are transient editor state and are not serialized into the motion asset. Preview, validation, inspection, and compilation consume the shared resolution and execution-record model; the shell does not calculate an alternative schedule.

## Key technical decisions

- `AnimaPlayback.reverse()` extends beyond `AnimaGroupMotion` to a leaf `AnimaPropertyMotion` and to `_AnimaSequence`/`_AnimaParallel` compositions of them: it replays with each leaf's `from`/`to` mirrored — the same technique `_AnimaRepeat` already uses for an alternating iteration — and reverses an `_AnimaSequence`'s child order. Reversing before a captured start value exists is a no-op. This contract already claims coverage for leaf, `Sequence`/`Parallel`, `AnimaGroupMotion`, and `AnimaGridMotion` reversal — reported backward-playback breakage is therefore treated as a regression or an untested path in that existing implementation, not a missing decision; stories should reproduce it per motion kind before changing the reversal mechanism itself.
- `Anima.play_backwards()` is a distinct operation from `AnimaPlayback.reverse()`, not a variant of it: `reverse()` flips a playback already in progress and requires something captured to flip to; `play_backwards()` starts a playback already flipped, with nothing to capture yet. Both share the same `build_reversed()` per motion kind, just at different times.
- Reversing an `_AnimaRepeat` follows the same rule already applied to leaf/`Sequence`/`Parallel` reversal — build a fresh reversed motion and restart from the top, never resume mid-cycle: `AnimaRepeatInstance.build_reversed()` wraps `child`'s own `build_reversed()` in a new `_AnimaRepeat` with the same `count`/`delay_between`/`alternate`. An infinite (`count = -1`) repeat reversing just continues infinitely in the reversed direction; an alternating repeat keeps alternating against the reversed child. No completed-iteration bookkeeping is needed because nothing resumes mid-cycle — resolves the backlog's "Repeat reversal rules" spec gap.
- `on_started`/`on_completed` are unrelated to the still-open "callback reversal mechanism" spec gap: that gap concerns the mid-timeline Callback leaf type and whether it needs explicit forward/backward behaviour or undo semantics. `on_started`/`on_completed` are pure lifecycle notifications with no state to undo, so they don't need a reverse policy of their own.
- `AnimaMotion.delay`/`delay_basis` extend to root-level playback this phase: `AnimaPlayback` now waits `delay` seconds (relative to `delay_basis`) before the first frame actually advances the target, for any motion played directly through `Anima.play()`/`.play_backwards()`, not only a motion nested inside an `_AnimaSequence` — this is what v1's `play_with_delay` needs and what a root-level motion could not previously do on its own.
- `AnimaPlayback.pause()`/`.resume()`/`.cancel()` already apply uniformly to single, group, and Grid motion playback — no motion-type-specific interruption code is needed or permitted (item 13).
- Target filters run before ordering. Odd/even filters use zero-based resolved-list parity and cannot be combined with each other.
- Grid motion shares the group scheduler and execution record. It never owns a second target-resolution, timing, reversal, or compilation model.
- Parallel groups start all valid targets together and use their completion policy; sequential groups wait for the actual completion of each item; staggered groups schedule by rank regardless of individual duration.
- Lifecycle changes, duplicate/empty targets, and reversal are explicit states. Reversal reuses the execution record and never reshuffles random order.
- The Composer shows configuration, resolved targets, and generated per-target timing; these are read-only projections of one execution record, not source motions.
- Compilation requires static deterministic resolution; runtime-only sources, live membership, callbacks, unresolved references, and non-deterministic order block it.
- Reduced motion may remove staggering or simplify presentation while preserving visibility and completion. Tests cover parity, origins, waves, and deterministic random seeds.
- Composer setup and inspection share one editor session and mutate the authored resource directly; no visual-only motion format or duplicate schedule is allowed.
- Pivot resolves to Godot's native `Control.pivot_offset` rather than custom per-frame transform compensation — it reuses the engine's own scale/rotation origin instead of a second mechanism.
- The Motion Composer's Inspector entry point is detected by property hint (`PROPERTY_HINT_RESOURCE_TYPE` naming `AnimaMotion`) on the selected node's script, not a required base class or interface — any node with an exported `AnimaMotion` field qualifies.
- `AnimaMotion.CompletionValuePolicy`/`CancellationValuePolicy` are new, distinct enums from the existing `AnimaGroupMotion.CompletionPolicy`/`_AnimaParallel.CompletionPolicy` — same English word, unrelated fields, unrelated meaning (value left behind vs. when a composite counts as done). Never conflate or merge them.
- `cancel()`'s `COMPLETE` value policy changes only the value applied on cancellation, never the signal semantics: it still emits `finished(false)` and never calls `on_completed_callback`, preserving the existing "success only means a genuine finish" invariant.
- `AnimaPropertyMotionInstance._advance_spring()`'s physics integration switches from raw `delta` to the same `motion.speed`-scaled delta already used for `_elapsed` — today `speed`/`speed_scale` shift when a spring is considered settled without changing how fast it visibly moves; this closes that gap rather than adding a new one.
- `AnimaPlayback._advance()` checks `is_instance_valid(target)` each frame and cancels when it fails — the fix for the Phase 10 review's discarded-but-uncancelled-playback leak, and the only new mechanism `Lifecycle-safe playback policies` requires; the other five recommended defaults already hold via existing Godot/Anima behaviour and needed no code change, only documenting.
- `Anima.reduced_motion` resolves against the existing `AnimaBehaviour.ReducedMotion` tri-state rather than existing alongside it as an unrelated second flag — `SYSTEM`/no-behaviour defers to the global switch, `ENABLED`/`DISABLED` always win locally. The pre-animation-snapshot reuse (`restore_initial()` reading each instance type's existing `CURRENT_AT_MOTION_START` capture) remains a deliberately minimal placeholder for not-yet-built per-property ownership tracking — see the phase brief's Assumption Log.
- `AnimaKeyframeMotion` is a new leaf type parallel to `AnimaPropertyMotion`, not a composite of several property motions — one `_elapsed`/`duration` clock drives every track together. Both authoring surfaces (`Motion.keyframes()`'s dictionary form, `.at()`'s fluent form) funnel through the same per-declaration merge/parse path, so equivalence between them is structural, not a separately-maintained guarantee.
- `AnimaEase.mirrored()` (ported from Anima v1's `get_mirrored_easing()`) swaps a named `EASE_IN_*`/`EASE_OUT_*` kind for its opposite, used by keyframe reversal so a reversed segment's easing shape actually feels reversed, not just replayed with the same shape backward. Easing *ownership* shifts by one stop on reversal (see §Keyframe motions), it isn't simply mirrored in place.
- A group or grid may nest another group or grid as its `item_motion` with no new mechanism: per-item target-passing and `CHILDREN`/`DESCENDANTS` resolution against the currently-received target already compose correctly through ordinary recursive `advance()` (see §Grid motion contract).
- `AnimaValue` is one polymorphic Resource with a `Kind` discriminator, not a subtype per source or operation — the same shape `AnimaEase` already uses for its own many kinds, chosen for the same reason: sources and arithmetic operations need to nest inside each other uniformly (an operand is itself sometimes another `AnimaValue`), which a single field-compatible shape supports directly.
- `AnimaValue.root(property)` reads the group's own container when resolving inside a group/grid item, never an individual item — this is the concrete answer to "what does root mean," closing the open risk the phase brief recorded; it matches v1's own `_root_node` override, which likewise defaulted to the animated node rather than any per-child target.
- `AnimaGroupCompiler.check_eligibility()` gains one more blocker, `Blocker.DYNAMIC_VALUE`, for an item motion whose `from_value`/`to_value` is an `AnimaValue` — the same "runtime-only source blocks static compilation" rule `RUNTIME_ONLY_TARGETS`/`LIVE_MEMBERSHIP` already enforce, not a new rule.
- `Anima.grid(container)` needs no per-property dispatch the way `Anima.on(target)` does, because it only ever builds one resource kind (`AnimaGridMotion`); its factory exists solely to keep `container` in scope across the chain so `.play()` can call `Anima.play(_motion, container)` without asking the caller to repeat it.
- `AnimaGridMotionFactory.keyframes()` shares its name with `AnimaOnMotionFactory.keyframes()` on purpose (one consistent verb for "author a keyframed item motion here") but not its return type — it returns the factory, not the built `AnimaKeyframeMotion`, because `AnimaGridMotionFactory`'s whole chain is built around returning itself so `.play()` stays reachable at the end, unlike `AnimaOnMotionFactory`'s semantic methods (which return the motion because nothing needs to chain after a single-target play).
- `AnimaGridMotionFactory.with_duration()`/`.with_ease()` exist because `.keyframes()` returning the factory (not the motion) would otherwise leave no way to set the built keyframe motion's easing inside the same fluent statement — `AnimaKeyframeMotion` already has `.with_duration()` but had no `.with_ease()` at all until this update, which is also what let `Anima.on(target).keyframes({...}).with_duration(...).with_ease(...)` chain directly onto `AnimaOnMotionFactory.keyframes()`'s own returned motion, no factory-level change needed on that side.
- `AnimaGridMotionFactory`'s `distance_formula` default (`EUCLIDEAN`) and `.with_dimensions()`'s auto-derived centred `start_point` are both factory-level conveniences layered on top of `AnimaGridMotion`'s own unrelated general-purpose defaults (`ROW`, `Vector2i.ZERO`) — the shorthand's own common case (radiate outward from the middle) differs from what a hand-built `AnimaGridMotion` should assume with no author input at all, so the two stay deliberately different rather than changing the underlying resource's own defaults for every caller.
- The auto-derived `start_point` is tracked as explicit-vs-derived with a private flag, not inferred from chain order — an explicit `.with_start_point()` call must never be silently overwritten by a `.with_dimensions()` call that happens to come later in the chain, and must still be respected if it came first.
- `AnimaEase.from(value: Variant)` exists so neither `with_ease()` needs a caller to hand-build an `AnimaEase` resource just to name a curve — accepting a bare `AnimaEase.Kind` for the common case (v1's own ergonomics) while still accepting a full `AnimaEase` for a parameterised curve (spring, bezier, elastic, …) that a bare `Kind` can't carry. Scoped to phase-14's two `with_ease()` additions only; `AnimaPropertyMotion.ease`/`.with_ease()` keep their existing `AnimaEase`-only signature, untouched.
- A keyframe stop's `_pivot` is authoring convenience only — v1 let an author declare `pivot` inline with whichever stop felt natural, but pivot itself is a resolve-once, whole-transform setting the same way `AnimaPropertyMotion.pivot` already is, so it was never a per-stop *value* that could meaningfully change mid-animation. `AnimaKeyframeMotionInstance` resolves exactly one pivot for the whole motion (first declared `_pivot` found, scanning tracks then stops in order; `default_pivot` otherwise), the same one-shot timing `AnimaPropertyMotion.pivot` uses — not a new per-stop-varying mechanism.
- The pivot anchor table and target-branching move from `AnimaPropertyMotionInstance` into the shared `AnimaMotionInstance` base (`_apply_pivot_to(target, pivot)`) so `AnimaKeyframeMotionInstance` can reuse the identical math instead of a second copy — the same "shared helper on the base instance class" precedent `_resolve_dynamic()` already set for dynamic values.
- `Anima.grid()`'s new `grid_size: Variant` parameter dispatches on `typeof()` because GDScript has no union parameter types — every accepted shape (`Vector2i`, `Vector2`, `Node`, `null`) funnels into the exact same dimension-setting path `.with_dimensions()` already uses, so "dimensions got set" stays one behaviour with one auto-derived-`start_point` rule, regardless of whether it happened through the constructor shorthand or the fluent call.
- Grid-size inference from a `Node` always reads child count from `container`, never from the inference-source node, even when a caller passes a different node than `container` as `grid_size` — the resolved `grid_dimensions` has to match how many things `container` actually has to lay out, which the inference-source node doesn't necessarily know.
- Every distance-formula preset method (`.radial()`, `.box()`, …) is pure sugar for `.with_distance_formula(DistanceFormula.X)`, one name per formula with no aliases — no preset carries independent state or behaviour, so none of them can drift out of sync with `.with_distance_formula()` itself, and there's no second name to keep in sync either.
- `AnimaGridMotionFactory`'s default `item_motion` is a distance-formula-preset-only convenience, not a construction-time one: each of the 13 preset methods applies `DEFAULT_ITEM_MOTION`/`DEFAULT_DURATION`/`DEFAULT_EASE` itself, guarded by `item_motion == null`, rather than `_init()` setting it unconditionally for every `Anima.grid()` call. `Anima.grid(container)` alone, or `.with_distance_formula(...)` used directly instead of a named preset, still requires an explicit `.with_item_motion()`/`.keyframes()` call same as before — only the one-liner preset methods get a free default, since those are the ones meant to work with nothing else supplied. Setting `item_motion` before calling a preset leaves it alone (the null check finds it already set); setting it after still simply overwrites, same as any other chain call — no "was this the default?" flag needed either way. `AnimaGridMotion`'s own hand-built default (`item_motion` unset) and `AnimaKeyframeMotion.default_ease`'s own general `LINEAR` default are deliberately untouched, matching the existing "factory-level conveniences never change the underlying resource's own defaults" pattern.
- A keyframe track missing its offset-`0.0` stop gets one synthesised at parse time, valued `AnimaValue.target(track.property_path)` — reusing this phase's own Dynamic Values resolution rather than giving `AnimaKeyframeMotionInstance` a second, bespoke "capture the target's live value" mechanism the way the older `AnimaPropertyMotionInstance` has (`_from_value_captured` + `target.get_indexed()`, resolved at first `advance()`, not at parse time). The two leaf types now infer a missing initial value through genuinely different mechanisms and at different moments (parse-time synthesis vs. first-advance runtime capture) — a deliberate, recorded divergence, not an oversight: unifying them would mean either teaching `AnimaPropertyMotion` to route through `AnimaValue` (out of this phase's scope) or giving keyframes their own capture flag (duplicates machinery `AnimaValue` already provides).
- `.play()` resolves its target per leaf rather than once at the composite root (phase-15) so a `.then()`/`.with()` chain can combine `Anima.on()` motions built against *different* nodes under one call — matching v1's own ability to declare independently-targeted animations together. The alternative (one target per `AnimaPlayback`, required to match every leaf) would have made `.play()` useless for exactly the multi-node case it exists to simplify; per-leaf resolution costs nothing for the common single-target case, since a leaf with no `convenience_target` of its own already falls back to the playback-supplied target unchanged.
- `AnimaPivot` moved out from under `AnimaPropertyMotion` into its own standalone `enum Kind`-holding class (phase-15) because the same pivot type is consumed by `AnimaKeyframeMotion`/`AnimaKeyframeStop` too — nesting it under one specific leaf motion type made every other consumer name a class that wasn't conceptually theirs. Values and ordinals are unchanged from the old `AnimaPropertyMotion.Pivot`, so a value serialized before the rename still resolves identically.
- `AnimaGridMotionFactory` gains `.then()`/`.with()` (phase-15) by stamping `motion.convenience_target = container` at construction and delegating to the built `AnimaGridMotion`'s own inherited chain methods — no new composition mechanism, reusing exactly what `.play()`'s per-leaf target resolution (§Target-bound authoring contract) already provides.
- `AnimaMotion.then()`/`.with()` accept a raw motion factory directly (phase-15), not just an already-built `AnimaMotion`, via a `"motion" in other` duck-typed check rather than a shared interface/base class — GDScript has no structural-typing-friendly interface mechanism cheaper than this for two unrelated `RefCounted` hierarchies (`AnimaMotion` and every `Anima.*MotionFactory`). Every convenience factory must expose a `motion: AnimaMotion` property under this exact name for `.then()`/`.with()` to recognize it — a durable contract every convenience factory follows, `AnimaGroupMotionFactory` included (§Group convenience shorthand).
- `AnimaParallelInstance` now reads each child's own `delay` as an offset from the parallel's own start (phase-15), rather than ignoring it — the natural reading once `.then()`/`.with()` made it trivial to author `motion.with_delay(N)` on a child *before* combining it with `.with(...)`, where the field previously did nothing silently. `delay_basis` is deliberately not consulted here (only `_AnimaSequence` steps have a "previous" for it to mean anything); a parallel child's delay is always "from this group's own start."
- `AnimaMotion.with_delay(value: float) -> AnimaMotion` is promoted from a leaf-only method to a base-class one: it sets the inherited `delay` field and returns `self`, exactly like the existing `AnimaPropertyMotion.with_delay()`/`AnimaKeyframeMotion.with_delay()` overrides already did, only now every `AnimaMotion` subtype inherits it for free — including `_AnimaSequence`/`_AnimaParallel`, the composite types `.then()`/`.with()` return. This is what "delay the whole composed chain" needs, and nothing else: `AnimaPlayback` already reads `motion.delay` at the playback root before the first frame advances (an existing decision — see the `delay`/`delay_basis` root-level bullet above), so `chain.with_delay(1.0).play()` was only missing the chain method itself, not new playback behaviour. No separate `play_with_delay()` name is introduced — reusing `with_delay()` keeps one verb for "delay this" everywhere it applies, leaf or composite, which is more consistent than a second name for the same field. The two leaf overrides are unchanged and keep narrowing their return type to their own subtype (`AnimaPropertyMotion`/`AnimaKeyframeMotion`) so duration/ease chaining still works after them; `_AnimaSequence`/`_AnimaParallel` (and any other subtype that doesn't need a narrower return) fall through to the new base implementation untouched.
- `AnimaGridMotionFactory.wait(seconds: float) -> AnimaGridMotionFactory` and `AnimaGroupMotionFactory.wait(seconds: float) -> AnimaGroupMotionFactory` delegate to `_motion.wait(seconds)` and return the factory (not the motion), the same delegation shape `.with_delay()`/`.on_started()`/`.on_completed()` already use on both factories — without this, `.wait()` set between two `Anima.grid(...).radial()`/`Anima.group(...)` calls in a chain would have no factory-level method to land on. `AnimaOnMotionFactory` needs no equivalent: its semantic methods (`.move_by()`, `.fade_in()`, …) already return the built `AnimaMotion` directly, so the base `.wait()` below is reachable on it with no factory indirection.
- `.wait(seconds: float) -> AnimaMotion` is a new `AnimaMotion` chain method that delays the *next* motion combined via `.then()`/`.with()`, not the motion `.wait()` is called on. It sets a transient, non-exported `_pending_chain_wait: float` field (the same "transient, non-serialized chain-authoring state" category `convenience_target` already established) on the motion it's called on, and does nothing else — no field on the receiver's own `delay` changes. `.then(other)`/`.with(other)` both read `self._pending_chain_wait` after resolving `other` via the existing `_resolve_chainable()` (§Target-bound authoring contract): if non-zero, they add it to the resolved motion's own `delay` (`resolved.delay += self._pending_chain_wait`) before appending/folding it in, then reset `self._pending_chain_wait` back to `0.0` so it's consumed exactly once, by the very next `.then()`/`.with()` call. Adding rather than replacing is what makes `.wait(1.0)` composed with an already-`with_delay(0.5)`-tagged child total `1.5`, per the item's own worked example — an explicit `with_delay()` on the next step and a preceding `.wait()` are two independent delay sources that stack, not one overriding the other. Calling `.play()` (or ending the chain) with a `.wait()` left unconsumed is a no-op leftover, not an error — nothing ever reads a motion's own `_pending_chain_wait` except the next `.then()`/`.with()`.
- `Anima.group()` (§Group convenience shorthand) accepts either a container `Node` (children become targets, `AnimaTargetCollection.Kind.CHILDREN` — mirroring `Anima.grid()`) or an explicit `Array` of target `Node`s (`Kind.EXPLICIT`), dispatched the same way `Anima.grid()`'s own `grid_size: Variant` already dispatches on `typeof()`, since GDScript has no union parameter types. This directly answers the "own calling signature" question this phase's brief left open, per the human decision to support both forms in one factory rather than two separate entry points.
- The composite motion *resource* classes beneath `Motion.sequence()`/`.parallel()`/`.repeat()`/`.race()`/`.conditional()`/`.stagger()` are renamed from `AnimaSequence`/`AnimaParallel`/`AnimaRepeat`/`AnimaRace`/`AnimaConditional`/`AnimaStagger` to `_AnimaSequence`/`_AnimaParallel`/`_AnimaRepeat`/`_AnimaRace`/`_AnimaConditional`/`_AnimaStagger`, a leading-underscore `class_name` convention that removes them from Godot's global autocomplete/"New Resource" listing prominence the same way GDScript already treats an underscore-prefixed name as internal-by-convention. This is a rename only: same fields, same `extends AnimaMotion`, same runtime behaviour, same serialized data shape (Resource identity is the script path/UID, not the `class_name` string, so already-saved `.tres` files referencing these types are unaffected). Scope is deliberately the *composite resource* classes only — `AnimaGroupMotion`/`AnimaGridMotion` stay public (they back `Anima.group()`/`Anima.grid()` directly), `AnimaPropertyMotion`/`AnimaKeyframeMotion` stay public (inspectable leaf types), and the various `*Instance`/`*Playback` runtime classes are unaffected (already never user-constructed, lower priority, left for a future pass). `_resolve_chainable()`'s existing `type_string()`-based error message (§Target-bound authoring contract) now names the underscore-prefixed type on an unresolvable `.then()`/`.with()` argument — an acceptable, even clarifying, side effect: it now visibly signals "not a type you construct directly" rather than looking like just another public class.

## API documentation pipeline

Public GDScript `##` comments are the canonical API documentation. A Node generator using only built-in modules reads public `class_name` declarations and their documented public members, then writes the Hugo API pages before the documentation site is served or built. Generated pages are never hand-edited; a code comment change is the documentation change.

The generator recognises the contiguous `##` block directly above a public class, function, property, signal, enum, or enum value. It preserves the comment’s Markdown and Godot cross-reference markup, and derives the class name, inheritance, member signatures, and member categories from the declaration. It rejects a public declaration without a preceding documentation block, so missing in-editor help also fails the API-doc generation step.

For each public class, generation produces the existing online-reference shape: front matter, one-line description, Overview, Inheritance, Availability, Quick example, and only the applicable Properties, Methods, Signals, Enumerations, and Constants sections. Conditional material such as determinism, performance, reduced motion, and interruption behaviour comes from the corresponding source comment only when that API has the behaviour.

`npm run docs:api` regenerates the API pages. `npm run dev` and `npm run build` run that command before their existing Hugo command, so local previews and production output use the same generated pages. No separate documentation database, metadata file, or third-party parser is introduced.

## Out of Scope

- Legacy dictionary or group-migration compatibility layers.
- Anima V1 target-bound aliases or migration shims.
- Anima V1's dynamic-value string-expression syntax (e.g. `.from("-.:size:x")`) — no parser or compatibility layer; the typed `AnimaValue.*` API is the only authoring surface.
- A heterogeneous per-target motion mapping resource; groups apply one item motion template.
- Native-code acceleration or an ECS architecture.

## Product principle constraints

- Group timing derives from relationships, ranks, and completion, not user-managed absolute timestamps.
- The same `AnimaGroupMotion` Resource is the source of truth for code, Inspector, and Motion Composer authoring.
- Deterministic execution records make random, centred, and index-origin groups inspectable and reversible.
- Every playback-ending operation (`cancel()`, `complete()`, `revert()`, `reverse()`) leaves a fully defined value and signal outcome — never an implicit or unhandled edge case.
- A target leaving the scene tree, being reparented, hidden, or the scene tree pausing, all have a defined playback response rather than undefined behaviour.
- A value resolved against live state never silently compiles to a fixed native curve — compile-eligibility treats an `AnimaValue`-backed property exactly like any other runtime-only source.
